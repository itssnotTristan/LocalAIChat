# Prompt for GPT-6 Sol

Build a real, installable, fully local AI chatbot for **Windows PC, Android, and iPhone running iOS 26**. I have a Windows PC and **do not own a Mac**. Develop and test on Windows first. Keep the same codebase and native inference architecture ready for Android and iOS, then move to iPhone testing only after the PC app works. I have limited iPhone sideload slots, so do not require repeated iPhone installs during early development.

## Outcome

Deliver working source code, a runnable Windows build, an Android build, an iOS Xcode project, and a downloadable iOS IPA that I can install from my Windows PC without owning a Mac. Use a hosted macOS/Xcode build runner for iOS compilation if needed; a cloud build is acceptable, but all AI inference and personal data processing must remain local on the user's device. Provide a documented Windows signing/install route, such as AltStore Classic/AltServer, using my own Apple Account on my own PC. Do not ask me to share my Apple password or signing credentials in chat or put them in a repository or build log. Build the actual app and inference integration. Do not stop at wireframes, scaffolding, mock model replies, a tutorial, or a web page. Use no paid cloud AI APIs, hosted inference, account requirement inside the app, or phone-to-PC inference relay. Once model files are acquired, **chat, image analysis, video analysis, speech recognition, and speech synthesis must work with airplane mode on each device**. Downloads may use the internet only when I explicitly initiate them.

Use a shared cross-platform UI such as Flutter if its current native plugin and platform support fit. Put inference behind a clear interface with native, in-process device backends, preferably llama.cpp/libmtmd or an equivalently proven local runtime. Desktop may use an app-owned local helper process if packaging makes that necessary, but the phone must perform inference on the phone. Use the same model metadata, conversation format, and feature tests across platforms. Research current official documentation and model licenses before finalizing libraries and models; pin working versions.

## Default model and multimodal input

Ship a **working default model profile that understands text and images and can describe video**. Assess a quantized, phone-sized vision model such as Qwen2.5-VL-3B-Instruct or SmolVLM2 Video, including its required vision projector, license, RAM use, context needs, and actual runtime support. Select the best model that passes end-to-end tests on the target hardware. Offer a smaller vision/video fallback for lower-memory phones if needed. Give the user exact model size and realistic minimum RAM/storage requirements. Do not describe a text-only model plus file picker as multimodal.

Allow an image from Files, Photos, camera, or clipboard. Show the image in chat and provide accurate visual descriptions, follow-up questions, and optional OCR. For video, let me choose a local file, sample representative frames with timestamps on-device, retain ordering, optionally transcribe its audio locally, and provide a timestamp-aware summary and answers about events in the clip. Let me control sampling density and show the sampled frames/timestamps so the result is auditable. Avoid claiming frame-perfect or full-motion understanding when analysis uses sampled frames. Do not send media off-device.

## Model management

Provide a model library where I can import, download, select, rename, inspect, and delete supported local models. Start with GGUF text and supported GGUF vision models, including model-plus-projector pairs; add other formats only if a tested backend actually supports them. Detect architecture, tokenizer/chat template, context limit, vision capability, quantization, file integrity, and estimated memory before loading. Explain unsupported files clearly. Do not claim every GGUF or arbitrary model will work. Support resuming downloads, checksum verification when available, enough-free-space checks, cancel/retry, and import from device file pickers. Keep model files in user-visible app storage with a documented backup/transfer path. A model switch must not silently discard a draft or conversation.

Provide hardware-aware settings: CPU/GPU acceleration where genuinely supported, threads, context size, max output, temperature/top-p when supported, memory warnings, token speed, load time, and a one-tap safe preset. Handle thermal throttling, backgrounding, low storage, cancellation, and out-of-memory errors without corrupting chat history.

## Adult conversations and control

I want a private chatbot for lawful adult/NSFW conversation, including explicit topics and consensual fiction. Do not add a blanket NSFW keyword filter, hidden cloud moderation, telemetry, or forced sanitized persona. Make system prompts editable and let me choose/import models that suit this use. Be honest that a base model's own training or license may still cause refusals; do not claim that a UI toggle can override them. Avoid implementing illegal sexual content or abuse of minors. Keep any age gate or distribution restriction required by the eventual platform separate from model inference, and explain any unavoidable distribution limits.

## Voice mode

Create an optional hands-free voice conversation mode with the feel of ChatGPT's voice interface, but entirely on-device: microphone input, local voice activity detection, streaming or low-latency speech-to-text, live transcript, streaming reply text, local text-to-speech playback, and barge-in so I can interrupt a spoken reply. Include push-to-talk, mute, stop, replay, selectable voices, output device/headset handling, and clear listening/thinking/speaking states. The voice mode must also work when the phone is offline. Consider a maintained local speech stack such as sherpa-onnx if its current models and licenses fit, and benchmark naturalness and latency on PC and mobile. Do not represent basic OS dictation or a cloud speech service as fully local voice mode. Clearly disclose whether the app can keep listening while in the background on each platform; implement only what the OS permits.

## Core app experience and useful extras

- Fast, polished, accessible chat UI with dark/light themes, streaming tokens, Markdown/code blocks, copy/share, edit and regenerate, stop generation, message search, pinned chats, folders/tags, and visible model/capability indicators.
- Multiple independent conversations, optional branches, drafts preserved after failed sends, configurable context/memory behavior, per-chat system instructions/personas, and a clear control to erase a chat or all data.
- Local import and export of conversations in readable formats such as JSON/Markdown, with optional password-protected encrypted backup; no automatic cloud sync.
- Local document Q&A for user-selected PDFs and text files with citations to local pages/sections. Store any index on-device and allow removing it. Keep this behind a feature flag until actual ingestion and retrieval work.
- Privacy screen lock with device biometrics/PIN where available, app storage protection, no analytics by default, a clear network activity indicator, and a one-tap offline mode that blocks non-download network use.
- Optional local tools only when each tool has a clear permission boundary. For example, file search may read only user-selected files. Never run arbitrary commands or alter files just because the model requested it.
- Accessibility: scalable text, screen reader labels, keyboard navigation on desktop, and understandable microphone/camera permission prompts.
